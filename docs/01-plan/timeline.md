# AI 디자이너 매칭 — 타임라인

## 전제

- 방식: Vision AI 태깅 (MVP) → 분기: 파인튜닝 또는 하이브리드
- 태그 체계: K-Hairstyle 데이터셋 분류 체계 참고
- 인프라: Supabase (PostgreSQL) + Next.js API Routes
- 1인 개발 기준 (풀타임이 아닌 경우 ×1.5~2)

## Phase 3: 데이터 축적 + 개선 (1~3개월)

> 목표: 다음 단계 전환을 위한 데이터 축적 + 서비스 품질 개선

| 기간 | 할 일 | 목표 |
|---|---|---|
| 1개월 | 유저 피드백 수집 + 태그 정확도 모니터링 | 문제점 파악 |
| 1개월 | 태그 체계 조정 (실사용 기반) | 불필요한 태그 제거, 누락 태그 추가 |
| 1~3개월 | 태깅 데이터 축적 | 목표: 5,000~10,000장 |

### 이 기간에 자동으로 쌓이는 것

```
유저 업로드 → Vision AI 태깅 → (이미지, 태그) 쌍 저장
디자이너 포트폴리오 업로드 → 자동 태깅 → (이미지, 태그) 쌍 저장
```

### Phase 3 종료 시 분기 판단

```
데이터 10,000장+ 축적
    ↓
┌─ 태그 매칭이 충분히 정확한가?
│
├─ YES → Route A: 파인튜닝 (비용 절감 + 속도 향상)
│
└─ NO, 태그로 못 잡는 뉘앙스가 문제 → Route B: 하이브리드 (태그 + 벡터)
```

---

## Phase 4 — Route A: 파인튜닝 전환 (2주)

> 조건: 태깅 데이터 10,000장+ 축적, 태그 매칭 품질이 충분함
> 목적: Vision AI API 비용 제거 + 속도 향상

### Week 1: 모델 학습

| 할 일 | 설명 |
|---|---|
| 학습 데이터 정제 | 오태깅 제거, 불균형 카테고리 보강 |
| ViT 파인튜닝 | Google Colab에서 학습 (Hugging Face Trainer) |
| 정확도 검증 | 테스트셋으로 평가, Vision AI와 비교 |

### Week 2: 전환 + 배포

| 할 일 | 설명 |
|---|---|
| 모델 HF Hub 업로드 | Hugging Face에 모델 배포 |
| API Route 전환 | Vision AI → HF 자체 모델 API |
| A/B 테스트 | 기존 Vision AI vs 파인튜닝 모델 비교 |
| 완전 전환 | Vision AI API 비용 제거 |

### 전환 효과

| | 전환 전 (Vision AI) | 전환 후 (자체 모델) |
|---|---|---|
| 비용 | 이미지당 ~$0.01 | 0원 |
| 속도 | 1~3초 | 수십ms |
| 외부 의존 | Anthropic/OpenAI | 없음 |
| 정확도 | 중간 (범용) | 높음 (헤어 특화) |

### Route A 이후 선택적 확장

파인튜닝 모델이 안정되면 Route B(하이브리드)를 추가로 도입 가능.

---

## Phase 4 — Route B: 하이브리드 전환 (3주)

> 조건: 태그만으로는 뉘앙스 매칭이 부족하다고 판단될 때
> 목적: 태그 정확성 + 벡터 뉘앙스를 결합한 최고 품질 매칭

### Week 1: 임베딩 파이프라인 복원

| 할 일 | 설명 |
|---|---|
| legacy/vector-embedding/ 코드 복원 | 기존 CLIP 임베딩 코드 재활용 |
| 헤어 CLIP 파인튜닝 | 자체 데이터로 임베딩 모델 학습 (헤어 특화) |
| pgvector 재활성화 | Supabase에 임베딩 컬럼 + 검색 함수 |

### Week 2: 하이브리드 매칭 로직

| 할 일 | 설명 |
|---|---|
| 태그 필터 → 벡터 정렬 | 태그로 후보 축소 → 벡터로 최종 순위 |
| 매칭 API 통합 | /api/match에 하이브리드 모드 추가 |
| 품질 비교 | 태그 단독 vs 하이브리드 A/B 테스트 |

### Week 3: 파인튜닝 추가 (선택)

| 할 일 | 설명 |
|---|---|
| 태깅 모델도 파인튜닝 | Vision AI 비용 제거 |
| 두 모델 통합 운영 | 분류 모델(태그) + 임베딩 모델(벡터) |

### 하이브리드 매칭 흐름

```
유저 이미지 업로드
    ↓
[태그 분류 모델] → 미디엄, 레이어드, 웜톤, 브라운
    ↓
태그로 DB 필터 → 300명 → 30명 (후보 축소)
    ↓
[임베딩 모델] → 업로드 벡터 vs 30명 벡터 비교
    ↓
벡터 유사도 순 정렬 → 최종 Top 5
    ↓
유저에게 결과: "93% 유사 — 웜톤 · 레이어드 일치" (설명 + 뉘앙스)
```

## 전체 타임라인 요약

```
  Phase 0     Phase 1     Phase 2       Phase 3              Phase 4
  (완료)      (2주)       (3주)         (1~3개월)
  ─────       ─────       ─────         ─────────           ┌─ Route A: 파인튜닝 (2주)
  ✅    ──→  MVP   ──→  실서비스  ──→  데이터 축적  ──→ 분기 ─┤
              데모        배포         5,000~10,000장        └─ Route B: 하이브리드 (3주)
```

| 마일스톤 | 시점 | 핵심 |
|---|---|---|
| MVP 데모 | **+2주** | 동작하는 프로토타입 |
| 실서비스 배포 | **+5주** | 디자이너 가입 + 유저 사용 |
| 분기 판단 | **+3~6개월** | 데이터 축적 후 방향 결정 |
| Route A 완료 | **+3~6개월 + 2주** | 자체 모델, API 비용 0 |
| Route B 완료 | **+3~6개월 + 3주** | 태그 + 벡터 최고 품질 |

### 분기 판단 기준

| 지표 | Route A (파인튜닝) | Route B (하이브리드) |
|---|---|---|
| 태그 매칭 유저 만족도 | 높음 (80%+) | 낮음 (60% 이하) |
| "비슷한데 왜 안 나와요" 불만 | 적음 | 많음 |
| 주요 문제 | API 비용/속도 | 태그로 못 잡는 뉘앙스 |
| 데이터 규모 | 10,000장+ | 10,000장+ |
